# پرامپت توسعه: سیستم احراز هویت ادمین + داشبورد چندشعبه‌ای (Multi-Branch) برای خیریه مکسا

> این فایل یک **سند مشخصات کامل (Spec)** است که باید به Claude Code داده شود تا قابلیت
> «احراز هویت ادمین» و «داشبورد چندشعبه‌ای» را روی پروژه‌ی فعلی پیاده‌سازی کند.
> همه‌چیز باید با **زبان طراحی فعلی**، **ساختار کد موجود**، و **استانداردهای امنیتی حرفه‌ای** هماهنگ باشد.

---

## ۰) شناخت پروژه (وضعیت فعلی — حتماً اول این را بخوان)

این یک سایت خیریه به زبان **فارسی (RTL)** با **PHP خام + PDO + MySQL/MariaDB** است.

**مسیرهای کلیدی:**
- وب‌روت: `public_html/`
- فرانت‌کنترلر عمومی: [`public_html/index.php`](../public_html/index.php) — صفحات را از روی جدول `pages` (بر اساس `slug`) رندر می‌کند؛ هر صفحه آرایه‌ای از کامپوننت‌هاست که از `dashboard/components/{name}/component.php` لود می‌شوند.
- روتر عمومی: [`public_html/core/router.php`](../public_html/core/router.php) — مسیرهای `/news/{slug}` و `/branch/{slug}` را هندل می‌کند (مسیر branch فعلاً stub است و جدولش وجود ندارد).
- داشبورد مدیریت: [`public_html/dashboard/index.php`](../public_html/dashboard/index.php) — پنل اصلی محتوا.
- کانفیگ دیتابیس: [`public_html/core/db-config.php`](../public_html/core/db-config.php) — اطلاعات اتصال را از خارج وب‌روت می‌خواند. **همیشه از این loader استفاده کن، هرگز اطلاعات دیتابیس را hard-code نکن.**
- توابع auth موجود: [`public_html/core/auth.php`](../public_html/core/auth.php) (`auth()`, `user()`, `can($level)`, `forbid()`) و [`public_html/core/middleware.php`](../public_html/core/middleware.php) (`require_role($level)`).
- دیتابیس نمونه: [`database/schema.sql`](../database/schema.sql).

**جدول‌های موجود مرتبط:** `pages`, `news`, `news_categories`, `campaigns`, `hero_slides`, `components`, `page_components`, `courses`, `employee_profiles` (همکاران), `roles` (ستون‌های `name`, `level`), `webusers`, `settings`, `audit_log`, `login_attempts`.

### ⚠️ مشکلات امنیتی فعلی که باید در این کار رفع شوند
1. **داشبورد هیچ محافظی (auth guard) ندارد** — `dashboard/index.php` و سایر صفحات داشبورد بدون هیچ بررسی ورود قابل دسترسی‌اند. هر کسی می‌تواند `/dashboard/` را باز کند.
2. **`dashboard/register.php` به هر کسی اجازه‌ی ثبت‌نام می‌دهد** و وارد پنل می‌شود. این باید کاملاً حذف/غیرفعال شود.
3. دو سیستم احراز هویت ناهماهنگ وجود دارد (`webusers` در `dashboard/login.php` و سشن در `core/auth.php`). باید **یک سیستم واحد و تمیز** جایگزین شود.

## ۱) هدف کلی

سه قابلیت به‌هم‌پیوسته ساخته می‌شود:

1. **سیستم لاگین ادمین:** ورود به داشبورد فقط با یوزرنیم/پسورد مجاز. دسترسی همه‌ی افراد غیرمجاز به داشبورد قطع شود. فقط **یک ادمین اصلی (ستاد مرکزی)** در ابتدا وجود دارد.
2. **شعبه‌ها (Branches):** مکسا شعبه‌های مختلف در ایران دارد (مثلاً «شعبه بیمارستان امام خمینی»). هر شعبه یک **صفحه‌ی اصلی اختصاصی** با همان ساختار صفحه‌ی اصلی مرکزی دارد و از طریق آدرسی مثل `mymacsa.ir/tabriz-branch` در دسترس است؛ مثل یک سایت مجزا برای آن شعبه عمل می‌کند (خبر، کمپین، صفحه اصلی و …).
3. **داشبورد چندشعبه‌ای (Multi-Tenant):** داشبورد فعلی به یک سیستم چندشعبه‌ای تبدیل می‌شود؛ ادمین مرکزی همه‌ی شعبه‌ها را مدیریت می‌کند، و هر شعبه ادمین و کاربران مخصوص خودش را دارد که فقط به محتوای همان شعبه دسترسی دارند.

## ۲) مدل نقش‌ها و دسترسی (Roles & Permissions)

سه سطح دسترسی:

| سطح | توضیح | حوزه‌ی دید |
|-----|-------|-----------|
| **ادمین مرکزی (Super Admin / HQ)** | تنها ادمین اولیه‌ی سیستم | همه‌ی شعبه‌ها + بخش «شعب» (ساخت/مدیریت شعبه) |
| **ادمین شعبه (Branch Admin)** | هنگام ساخت هر شعبه ساخته می‌شود | فقط محتوای شعبه‌ی خودش + مدیریت کاربران شعبه‌ی خودش |
| **کاربر شعبه (Branch User)** | توسط ادمین شعبه ساخته می‌شود | فقط بخش‌هایی که سمتش (role) اجازه می‌دهد، درون همان شعبه |

**اصل طلایی امنیت (Tenant Isolation):** دسترسی شعبه‌ای باید در **هر کوئری سمت سرور** اعمال شود (فیلتر `branch_id`)، نه فقط در UI. هیچ کاربری به هیچ روشی (تغییر URL، دستکاری پارامتر، IDOR) نباید به محتوای شعبه‌ی دیگر دسترسی پیدا کند.

## ۳) تغییرات دیتابیس (Schema)

> همه‌ی تغییرات باید به‌صورت یک فایل migration در `database/migrations/` نوشته شوند (مثلاً `001_multi_branch.sql`) و یک اسکریپت backfill برای داده‌ی موجود داشته باشند. فایل `database/schema.sql` هم باید به‌روزرسانی شود.

### ۳-۱) جدول `branches`
```sql
CREATE TABLE branches (
  id            INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name          VARCHAR(150) NOT NULL,            -- مثلا: شعبه بیمارستان امام خمینی
  slug          VARCHAR(100) NOT NULL UNIQUE,     -- مثلا: tabriz-branch  (فقط a-z0-9-)
  is_hq         TINYINT(1) NOT NULL DEFAULT 0,    -- ستاد مرکزی = 1 (فقط یک ردیف)
  status        ENUM('active','disabled') NOT NULL DEFAULT 'active',
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
- یک ردیف **ستاد مرکزی** (`is_hq=1`, مثلاً `slug='hq'` یا `name='ستاد مرکزی مکسا'`) به‌صورت seed ساخته می‌شود.

### ۳-۲) افزودن `branch_id` به جدول‌های محتوا
به جدول‌های زیر ستون `branch_id INT UNSIGNED NOT NULL` با `FOREIGN KEY` به `branches(id)` و ایندکس اضافه شود:
`pages`, `news`, `campaigns`, `hero_slides`, و هر جدول محتوای دیگری که per-branch می‌شود (`courses`, `employee_profiles`, …).
- **Backfill:** همه‌ی ردیف‌های موجود به `branch_id` ستاد مرکزی نسبت داده شوند (چون محتوای فعلی متعلق به شعبه‌ی مرکزی است).
- برای `pages`/`news` که `slug` یکتا دارند، یکتایی باید **ترکیبی** شود: `UNIQUE(branch_id, slug)` تا دو شعبه بتوانند صفحه‌ی `home` خودشان را داشته باشند.

### ۳-۳) کاربران داشبورد — `dashboard_users`
> به‌جای جدول‌های پراکنده‌ی فعلی (`webusers`)، یک جدول تمیز و واحد. `webusers` فقط برای پنل عمومی حامیان بود؛ آن را با این قاطی نکن.
```sql
CREATE TABLE dashboard_users (
  id            INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  branch_id     INT UNSIGNED NOT NULL,            -- شعبه‌ای که کاربر به آن تعلق دارد
  username      VARCHAR(60)  NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,            -- password_hash(PASSWORD_DEFAULT)
  full_name     VARCHAR(120) DEFAULT NULL,
  role_id       INT UNSIGNED DEFAULT NULL,        -- سمت (برای کاربران شعبه)
  is_super      TINYINT(1) NOT NULL DEFAULT 0,    -- ادمین مرکزی = 1
  is_branch_admin TINYINT(1) NOT NULL DEFAULT 0,  -- ادمین شعبه = 1
  status        ENUM('active','disabled') NOT NULL DEFAULT 'active',
  last_login_at DATETIME DEFAULT NULL,
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (branch_id) REFERENCES branches(id),
  FOREIGN KEY (role_id)   REFERENCES dashboard_roles(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### ۳-۴) سمت‌ها و دسترسی‌ها — `dashboard_roles`
```sql
CREATE TABLE dashboard_roles (
  id          INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  branch_id   INT UNSIGNED NOT NULL,              -- سمت‌ها per-branch تعریف می‌شوند
  name        VARCHAR(80) NOT NULL,               -- مثلا: خبرنگار
  permissions JSON NOT NULL,                      -- مثلا: ["news"] یا ["news","campaigns"]
  is_preset   TINYINT(1) NOT NULL DEFAULT 0,      -- سمت‌های از پیش تعریف‌شده مثل خبرنگار
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (branch_id) REFERENCES branches(id),
  UNIQUE(branch_id, name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
- **سمت‌های پیش‌فرض (preset)** مثل «خبرنگار» (`permissions: ["news"]`) برای هر شعبه seed شوند.

### ۳-۵) دسترسی‌های محتوای هر شعبه — `branch_features`
کدام بخش‌ها برای یک شعبه فعال‌اند (هنگام ساخت شعبه با چک‌باکس‌ها تعیین می‌شود):
```sql
CREATE TABLE branch_features (
  branch_id INT UNSIGNED NOT NULL,
  feature   VARCHAR(50)  NOT NULL,   -- hero | news | partners | campaigns | courses | pages | financial | feedback | medical | ...
  enabled   TINYINT(1) NOT NULL DEFAULT 1,
  PRIMARY KEY (branch_id, feature),
  FOREIGN KEY (branch_id) REFERENCES branches(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### ۳-۶) جدول donations / کمک‌ها (تصمیم نهایی)
یک ستون **`branch_id INT UNSIGNED NOT NULL`** مستقیم به `panel_donations` اضافه شود و **در لحظه‌ی ثبت کمک** مقداردهی شود طبق این قاعده:
- اگر کمک به یک **کمپین** (یا دوره‌ی) متعلق به یک شعبه پرداخت شده → `branch_id` = شعبه‌ی همان کمپین/دوره.
- اگر کمک **عمومی** است (کمک آنلاین بدون کمپین، `campaign_id IS NULL`) → `branch_id` = **ستاد مرکزی**.

قواعد نمایش:
- **مجموع کمک‌های هر شعبه** = فقط کمک‌هایی که `branch_id` آن‌ها برابر آن شعبه است (یعنی کمک به کمپین‌های خودِ شعبه).
- **کمک‌های عمومی فقط در ستاد مرکزی** محاسبه و نمایش داده می‌شوند و در داشبورد شعبه‌های دیگر **اصلاً دیده نمی‌شوند**.
- علت انتخاب ستون مستقیم (به‌جای join صرف روی `campaign_id`): `campaign_id` در `panel_donations` nullable است و کمک عمومی دارد؛ ضمناً با حذف یک کمپین، آمار شعبه نباید بشکند.

## ۴) بخش اول — سیستم لاگین و قفل‌کردن داشبورد

### ۴-۱) صفحه‌ی لاگین واحد
- یک صفحه‌ی لاگین تمیز بساز (پیشنهاد: `dashboard/login.php` بازنویسی شود) با همان **زبان طراحی فعلی داشبورد** (همان فونت Vazirmatn، رنگ‌ها، کارت‌ها، RTL).
- فقط فیلد یوزرنیم و پسورد. بدون لینک ثبت‌نام.
- **`dashboard/register.php` کاملاً حذف یا غیرفعال شود** (هیچ self-registration نباید وجود داشته باشد).

### ۴-۲) Bootstrap محافظ (auth guard)
- یک فایل bootstrap بساز (مثلاً `dashboard/_guard.php`) که در **ابتدای هر صفحه‌ی داشبورد** require شود و:
  1. سشن امن را شروع کند.
  2. اگر کاربر لاگین نیست → ریدایرکت به صفحه‌ی لاگین.
  3. کاربر، شعبه‌ی فعال، و دسترسی‌هایش را در `$_SESSION` لود کند.
  4. اگر کاربر `status = disabled` است → خروج فوری و پیام.
  5. دسترسی هر صفحه را بر اساس feature/permission بررسی کند (مثلاً صفحه‌ی خبر فقط برای کسی که permission `news` دارد).
- این guard باید روی **همه‌ی فایل‌های داشبورد** اعمال شود (index.php و همه‌ی `*-create.php`, `*-list.php`, `*-save.php`, …). هیچ endpoint داشبورد نباید بدون guard بماند.

### ۴-۳) Seed ادمین مرکزی
- یک اسکریپت CLI امن (مثلاً `database/seed-admin.php` که فقط از خط فرمان اجرا می‌شود، نه از وب) که یک رکورد ادمین مرکزی با `is_super=1` و `branch_id` ستاد مرکزی می‌سازد و پسورد را با `password_hash()` ذخیره می‌کند. یوزر/پسورد اولیه از ورودی یا متغیر محیطی گرفته شود (نه hard-code).

## ۵) بخش دوم — صفحات اختصاصی شعبه (فرانت عمومی)

- آدرس هر شعبه: `mymacsa.ir/{branch-slug}` (مثلاً `mymacsa.ir/tabriz-branch`).
- روتینگ (`public_html/index.php` و/یا `core/router.php` و `.htaccess`) باید:
  1. اول بررسی کند آیا `{slug}` با یک `branches.slug` مطابقت دارد → اگر بله، **صفحه‌ی اصلی آن شعبه** را رندر کند (از `pages` با `branch_id` آن شعبه و `slug='home'`).
  2. مسیرهای داخلی شعبه هم پشتیبانی شوند: `mymacsa.ir/{branch-slug}/news/{news-slug}`، کمپین‌ها و … — دقیقاً مثل ساختار مرکزی ولی scope‌شده به آن شعبه.
- **ساختار آدرس (تصمیم نهایی): top-level بدون پیشوند** — دقیقاً `mymacsa.ir/{slug}` مثل `mymacsa.ir/tabriz-branch`. **هیچ پیشوند `/branch/`** استفاده نشود.
- **جلوگیری از تداخل (اجباری):** فضای نام slug بین شعبه‌ها و صفحات مرکزی مشترک است، پس:
  - هنگام ساخت شعبه، slug باید یکتا باشد نسبت به **هم** `branches.slug` و **هم** `pages.slug` صفحات مرکزی (چک یکتایی سراسری + لیست slugهای رزروشده).
  - **ترتیب تشخیص در روتر:** اول `branches.slug` چک شود؛ اگر مطابقت داشت، صفحه‌ی اصلی شعبه رندر شود. در غیر این صورت به منطق فعلی صفحات مرکزی برود.
- ساختار رندر صفحه‌ی شعبه باید **همان مکانیزم component-based فعلی** باشد (همان `dashboard/components/*`)، فقط داده‌ها از ردیف‌های `branch_id`‌دار خوانده شوند.

## ۶) بخش سوم — داشبورد چندشعبه‌ای (UI/UX)

> به اسکرین‌شات ارائه‌شده توجه کن: «باکس ۱» = هدر بالای سایدبار (دکمه‌ی «داشبورد مدیریت»)، «باکس ۲» = منوی آیتم‌های سایدبار.

### ۶-۱) باکس ۱ → سلکتور شعبه (Dropdown)
- «باکس ۱» به یک **دراپ‌داون** تبدیل شود که لیست شعبه‌های تعریف‌شده را نشان می‌دهد.
- به‌صورت پیش‌فرض **ستاد مرکزی** انتخاب‌شده باشد.
- **فقط ادمین مرکزی** این دراپ‌داون را با همه‌ی شعبه‌ها می‌بیند. ادمین/کاربر شعبه فقط شعبه‌ی خودش را می‌بیند (دراپ‌داون غیرفعال یا تک‌گزینه‌ای).
- شعبه‌ی انتخاب‌شده در سشن نگه داشته شود و **منوی باکس ۲ و کل محتوای داشبورد بر اساس آن scope شود**.

### ۶-۲) باکس ۲ → منوی وابسته به شعبه‌ی انتخاب‌شده
- منو فقط آیتم‌هایی را نشان دهد که برای شعبه‌ی انتخاب‌شده در `branch_features` فعال‌اند و کاربر به آن‌ها permission دارد.
- اگر ستاد مرکزی انتخاب شده باشد: همان ساختار فعلی (هیروها، خبرها، همکاران، کمپین‌ها، دوره‌ها، کامپوننت‌ها و صفحات، مالی، …).

### ۶-۳) بخش «شعب» (فقط برای ادمین مرکزی)
- فقط در سطح دسترسی ستاد مرکزی، یک تیتر جدید در سایدبار به نام **«شعب»** (هم‌سطح «مدیریت محتوا» و «مالی») با دو زیرمنو:
  - **تعریف شعبه جدید**
  - **مدیریت شعبه‌ها**

## ۷) بخش چهارم — «تعریف شعبه جدید»

صفحه‌ای که این ورودی‌ها را می‌گیرد:

1. **نام شعبه** و **تگ/slug شعبه** (برای URL و انتساب داده‌ها در دیتابیس). slug را sanitize کن (فقط `a-z0-9-`) و یکتا بودنش را چک کن.
2. **یوزرنیم و پسورد ادمین شعبه** — یک رکورد در `dashboard_users` با `is_branch_admin=1` و `branch_id` همان شعبه ساخته می‌شود (پسورد با `password_hash`).
3. **دسترسی‌های محتوایی شعبه** — برای هر بخش زیر یک **چک‌باکس** (لیست نهایی و کامل بخش‌های قابل‌واگذاری):
   `hero` (هیروها)، `news` (خبرها)، `campaigns` (کمپین‌ها)، `partners` (همکاران)، `courses` (دوره‌ها)، `pages` (کامپوننت‌ها و صفحات)، `financial` (گزارش مالی)، `feedback` (انتقادات و پیشنهادات)، `medical` (پرونده‌های پزشکی).
   هر چک‌باکس فعال:
   - یک ردیف در `branch_features` ایجاد می‌کند.
   - زیرسیستم مجزای آن بخش را برای شعبه فراهم می‌کند (مثلاً اگر «هیرو» فعال شد، سیستم هیروی مستقل برای آن شعبه با `branch_id` خودش).
4. **دکمه‌ی «ایجاد شعبه»**.

### دایرکتوری شعبه
- یک دایرکتوری `public_html/branches/` ساخته شود و درون آن پوشه‌ای با **تگ شعبه** (مثلاً `public_html/branches/tabriz-branch/`).
- فایل‌های آپلودی و asset مخصوص آن شعبه (تصاویر هیرو، خبر، کمپین) در این پوشه ذخیره شوند.
- **توجه:** منبع حقیقت محتوا، دیتابیس است (ردیف‌های `branch_id`‌دار)؛ این پوشه برای **فایل‌ها/آپلودها**ی آن شعبه است. هر دو باید scope‌شده باشند.
- یک صفحه‌ی `home` پیش‌فرض برای شعبه در جدول `pages` با `branch_id` و `slug='home'` ساخته شود تا `mymacsa.ir/{tag}` بلافاصله کار کند.

> ⚠️ امنیت ساخت پوشه: نام پوشه دقیقاً از slug تأییدشده ساخته شود (هیچ‌گاه از ورودی خام). از path traversal جلوگیری شود.

---

## ۸) بخش پنجم — داشبورد اختصاصی ادمین شعبه

- وقتی ادمین شعبه (مثلاً تبریز) لاگین می‌کند، به **همان داشبورد اصلی** هدایت می‌شود، اما با **سطح دسترسی محدود**: فقط محتوای شعبه‌ی خودش را می‌بیند و ویرایش می‌کند.
- در صفحه‌ی اصلی داشبورد، **آمار مختص همان شعبه** نمایش داده شود:
  - تعداد کمپین‌های فعال آن شعبه.
  - مجموع کمک‌های جمع‌آوری‌شده که **فقط** به کمپین‌ها/دوره‌های آن شعبه پرداخت شده (`panel_donations.branch_id` = همان شعبه).
  - **کمک‌های عمومی (آنلاین بدون کمپین) در داشبورد شعبه نمایش داده نمی‌شوند** (فقط در ستاد مرکزی).
  - سایر آمار، همه scope‌شده به `branch_id`.
- ادمین شعبه **نباید** بخش «شعب» یا دراپ‌داون چندشعبه‌ای یا محتوای شعبه‌های دیگر را ببیند.

### داشبورد ستاد مرکزی (دید کلان)
- ستاد مرکزی علاوه بر محتوای خودش، **همه‌ی کمپین‌های همه‌ی شعب** را هم می‌بیند؛ هر کمپین در لیست با **تگ شعبه‌ای که آن را ساخته** مشخص می‌شود (نمایش `branch.name`/`branch.slug` کنار هر کمپین).
- کمک‌های عمومی (آنلاین) فقط در محاسبات و آمار ستاد مرکزی لحاظ می‌شوند.

---

## ۹) بخش ششم — مدیریت کاربران شعبه (برای ادمین شعبه)

در سایدبار ادمین شعبه، یک تیتر جدید با دو گزینه:

### ۹-۱) «افزودن کاربر»
- نام و نام‌خانوادگی کاربر.
- یوزرنیم و پسورد.
- **سمت (Role):**
  - انتخاب از سمت‌های از پیش تعریف‌شده (مثل «خبرنگار» که فقط به بخش خبرِ همان شعبه دسترسی دارد).
  - یا گزینه‌ی **«افزودن سمت جدید»**: نام سمت + چک‌باکس‌های دسترسی محتوا (خبر، کمپین، …) → یک ردیف در `dashboard_roles` با `permissions` به‌صورت JSON.
- کاربر ساخته‌شده `branch_id` همان شعبه و `role_id` انتخاب‌شده را می‌گیرد.

### ۹-۲) «مدیریت کاربران»
- لیست کاربران ساخته‌شده‌ی همان شعبه به‌همراه سمت و سطح دسترسی‌شان.
- امکان **فعال/غیرفعال کردن** هر کاربر (`status`). با غیرفعال‌شدن، کاربر دیگر نتواند وارد داشبورد شود (guard هنگام ورود و در هر درخواست چک کند).
- ادمین شعبه فقط کاربران شعبه‌ی خودش را می‌بیند و مدیریت می‌کند.

---

## ۱۰) الزامات امنیتی (Security Hardening) — اجباری

پیاده‌سازی باید در برابر تهدیدات سایبری مقاوم باشد:

- **هش پسورد:** فقط `password_hash()` / `password_verify()` (bcrypt/argon2). هرگز پسورد خام یا md5/sha1.
- **SQL Injection:** فقط prepared statements با PDO (پارامتری). هیچ کوئری با الحاق رشته‌ای ورودی.
- **CSRF:** توکن CSRF برای همه‌ی فرم‌ها و درخواست‌های POST/PUT/DELETE داشبورد.
- **XSS:** خروجی همه‌ی داده‌های کاربر با `htmlspecialchars()` escape شود. ورودی‌ها اعتبارسنجی شوند.
- **Session security:** `session_regenerate_id(true)` بعد از لاگین؛ کوکی با `HttpOnly`, `Secure`, `SameSite=Strict`/`Lax`؛ تایم‌اوت idle و absolute.
- **Brute-force:** محدودسازی نرخ تلاش ورود با جدول موجود `login_attempts` (قفل موقت بعد از چند تلاش ناموفق).
- **Authorization (مهم‌ترین):** ایزولاسیون شعبه در **هر کوئری سمت سرور** (فیلتر `branch_id`). هرگز فقط به UI اعتماد نکن. جلوگیری از IDOR: قبل از هر عمل روی یک رکورد، مالکیت شعبه‌ای آن رکورد تأیید شود.
- **Privilege checks:** بررسی permission در هر endpoint، نه فقط نمایش/عدم‌نمایش در منو.
- **Least privilege:** ادمین شعبه نتواند super-admin بسازد یا به منابع مرکزی دست بزند.
- **File upload/dir:** ساخت پوشه و آپلود فقط با نام sanitize‌شده؛ جلوگیری از path traversal؛ غیرفعال‌کردن اجرای PHP در پوشه‌های آپلود.
- **اطلاعات اتصال دیتابیس:** فقط از `core/db-config.php` (خارج از گیت). هیچ credential در کد.
- **Audit:** عملیات حساس (ساخت شعبه، ساخت/غیرفعال‌کردن کاربر، لاگین) در جدول `audit_log` ثبت شود.

---

## ۱۱) الزامات طراحی (UI) — اجباری

- **کاملاً منطبق با زبان طراحی فعلی داشبورد:** همان رنگ‌ها، تایپوگرافی (فونت Vazirmatn)، شعاع گوشه‌ها، کارت‌ها، فاصله‌ها، آیکن‌ها و الگوی سایدبار موجود.
- **RTL و فارسی** در تمام صفحات جدید.
- دراپ‌داون شعبه، فرم تعریف شعبه، فرم افزودن کاربر و جدول مدیریت کاربران باید با کامپوننت‌های موجود داشبورد یک‌دست باشند (همان استایل دکمه/اینپوت/جدول/مودال).
- ریسپانسیو و سازگار با موبایل (مثل بقیه‌ی داشبورد).

---

## ۱۲) محدودیت‌ها و نکات مهم

- **هیچ قابلیت موجودی نباید بشکند.** داشبورد فعلی برای ستاد مرکزی باید دقیقاً مثل قبل کار کند (فقط حالا scope‌شده به شعبه‌ی مرکزی و پشت لاگین).
- پنل عمومی حامیان (`webusers`, API در `public_html/api/`, `benefactor-dashboard/`) یک سیستم جداست؛ آن را با احراز هویت داشبورد قاطی نکن.
- migration باید روی دیتای موجود امن باشد (backfill شعبه‌ی مرکزی).
- کد تمیز، کامنت‌گذاری فارسی هم‌سطح فایل‌های موجود، و بدون افشای جزئیات خطا به کاربر (در production).

## ۱۳) خروجی‌های مورد انتظار (Deliverables)

1. فایل migration در `database/migrations/` + به‌روزرسانی `database/schema.sql`.
2. اسکریپت seed ادمین مرکزی + seed شعبه‌ی مرکزی + سمت‌های preset.
3. صفحه‌ی لاگین واحد + bootstrap محافظ (`_guard.php`) اعمال‌شده روی همه‌ی صفحات داشبورد.
4. حذف/غیرفعال‌سازی `register.php`.
5. سلکتور شعبه (باکس ۱) + منوی scope‌شده (باکس ۲) + بخش «شعب».
6. صفحه‌ی «تعریف شعبه جدید» + ساخت دایرکتوری شعبه + provisioning بخش‌ها.
7. روتینگ فرانت `mymacsa.ir/{slug}` برای صفحات شعبه.
8. داشبورد ادمین شعبه با آمار scope‌شده.
9. صفحات «افزودن کاربر» و «مدیریت کاربران» با سیستم سمت‌ها.
10. اعمال کامل الزامات امنیتی بخش ۱۰.

---

## ۱۴) پیشنهاد ترتیب اجرا (فازبندی)

> پیشنهاد می‌شود کار فاز‌به‌فاز انجام و بعد از هر فاز تست شود:

1. **فاز ۱ — امنیت پایه:** سیستم لاگین واحد + guard روی کل داشبورد + حذف register + seed ادمین مرکزی. (داشبورد فعلی پشت لاگین قفل می‌شود.)
2. **فاز ۲ — مدل شعبه:** جدول `branches` + افزودن `branch_id` به محتوا + backfill مرکزی. (بدون تغییر ظاهری، داده‌ها scope می‌شوند.)
3. **فاز ۳ — داشبورد چندشعبه‌ای:** سلکتور شعبه + منوی scope‌شده + بخش «شعب» + «تعریف شعبه جدید» + دایرکتوری/provisioning.
4. **فاز ۴ — فرانت شعبه:** روتینگ `mymacsa.ir/{slug}` + صفحه‌ی اصلی و بخش‌های شعبه.
5. **فاز ۵ — کاربران شعبه:** سمت‌ها + افزودن/مدیریت کاربر + فعال/غیرفعال.
6. **فاز ۶ — سخت‌سازی نهایی امنیت و تست نفوذ سبک:** بازبینی همه‌ی نقاط (CSRF, IDOR, isolation, rate-limit).

---

### تصمیمات معماری نهایی‌شده (قطعی — طبق تأیید کارفرما)
1. **انتساب کمک به شعبه:** ستون مستقیم `branch_id` روی `panel_donations`. کمک به کمپین/دوره‌ی یک شعبه → آن شعبه؛ کمک عمومی آنلاین (بدون کمپین) → فقط ستاد مرکزی و در شعب نمایش داده نمی‌شود. ستاد مرکزی همه‌ی کمپین‌های همه‌ی شعب را با تگ شعبه می‌بیند. (بخش ۳-۶ و ۸)
2. **آدرس شعبه:** top-level بدون پیشوند (`mymacsa.ir/tabriz-branch`)، با چک یکتایی سراسری slug و اولویت تشخیص شعبه در روتر. (بخش ۵)
3. **بخش‌های قابل‌واگذاری:** `hero`, `news`, `campaigns`, `partners`, `courses`, `pages`, `financial`, `feedback`, `medical`. (بخش ۷-۳)
